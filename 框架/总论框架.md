# 第二大脑总论框架

> 📌 本文档定义设计哲学和系统定义。数据流的完整六层视图见「二、系统架构 → 4. 架构流程 — 六层数据流」。

## 一、设计哲学

### 根本定位

第二大脑是一个**个人持续迭代系统**。

### 核心目的

- 更高效地学习一切感兴趣事物的底层逻辑，满足好奇心，体悟智慧。
- 量化人生轨迹，看见自己的成长。
- 支撑信息的完整闭环：**收集 → 整合 → 梳理 → 学习 → 复盘 → 内化 → 再执行**。

### 运作原理

| 分工 | 职责 |
|------|------|
| **系统** | 存储所有数据，让信息可检索、可关联、可对比 |
| **AI** | 加速信息聚拢、对比、结构化——让人看见自己看不见的关联 |
| **人** | 负责判断、内化、决策——AI 不做人的大脑，只省掉纯检索和纯计算 |

### 四条原则

1. **知识在于链接，不在于分类**。文件夹是骨架，双向链接是灵魂。
2. **盖尔定律**。从简单有效的系统开始，逐步迭代。不过度设计。
3. **奥卡姆剃刀**。若无必要，勿增实体。
4. **单一事实源**。每个规则只在最自然的归属框架中定义一次，其余框架通过 `[[框架名#节标题]]` 引用，不重复。修改规则只需改一处。

## 二、系统架构

>  第二大脑分为三层：知识层、执行层、复盘层。三层形成闭环。

### 1. 知识层 — 笔记库

| 分类        | 定位   | 说明                                                                      |
| --------- | ---- | ----------------------------------------------------------------------- |
| **待处理笔记** | 收件箱  | 外部信息快速入口（网址、视频、素材）。行动想法走起念                                              |
| **常青笔记**  | 零散认知 | 自己提炼的认知碎片。靠双链连接。内部按演进阶段标注：`#识` → `#道` / `#术`                            |
| **系统笔记**  | 体系网络 | 系统学习某个领域的路径网络。在实现目标的过程中碰壁 → 学习 → 填补网络。内部按领域建子文件夹，各领域自成体系。使用与常青笔记相同的模板结构 |
| **菜谱**    | 数据资产 | 食材、做法、经验记录。支撑小程序                                                        |
| **图书馆**   | 书库   | 管理书籍生命周期。独立于三层循环，阅读产出经书摘→待处理笔记汇入知识层                                     |

> 知识层详细操作见 [[笔记系统框架]]、[[菜谱框架]]、[[图书馆框架]]。

**流向**：

```
待处理笔记 → 常青笔记(#识) → 升级为道(#道) / 拆解为术(#术)
            → 系统笔记
```

**常青笔记标签（道·识·术）**：

| 标签 | 含义 | 来源 |
|------|------|------|
| `#识` | 阶段性认识、发现 | 从观察到提炼的跳跃。可能偏，可修正 |
| `#道` | 根本规律、原则 | 经过多次验证的识，稳定沉淀为世界观 |
| `#术` | 实践方法、操作 | 从道和识推导出的行动指南 |

演化规则：`#识` 经过实践反复验证 → 升为 `#道`。`#道` 拆解为可执行步骤 → 生 `#术`。

区分：脑内行动想法（如"我想练琴"）→ 起念。外部素材（网址、视频）和对某个概念、现象、方法的模糊认识 → 待处理笔记。

### 2. 执行层 — 行动引擎

| 分类               | 定位     | 说明                                    |
| ---------------- | ------ | ------------------------------------- |
| **工作待办** | 工作执行 | 日常工作中具体要做的事 |
| **系统迭代待办** | 个人成长执行 | 健身、音乐等长期系统，一个系统一个大标题，零星待办列在标题下 |
| **obsidian架构待办** | 系统维护 | Obsidian 优化、知识库调整等具体动作 |
| **起念**           | 行动的想法  | 脑内冒出的行动的点子。不设日期、不定优先级。成熟后按性质分流到以上三类待办 |

关系：起念 → 按性质分流 → 工作 / 系统迭代 / obsidian架构待办。

> 执行层详细操作见 [[待办事项框架]]。

### 3. 复盘层 — 反思引擎

| 分类          | 定位    | 说明                                                             |
| ----------- | ----- | -------------------------------------------------------------- |
| **日复盘**     | 每日运转  | Tasks 自动归集今日任务 + 完成记录，手动反思形成日志总结<br>Tracker 热力图量化长期迭代，迭代项目可视量化 |
| **周/月/年复盘** | 阶段性审视 | 更长周期的趋势分析与方向校准                                                 |

**复盘产出分流**：

```
日复盘反思
    ├── 清晰认知（零散）→ 常青笔记 #识
    ├── 清晰认知（属某体系）→ 系统笔记
    ├── 模糊知识性思考 → 待处理笔记/随笔
    └── 行动的想法 → 起念
```

**所有分流均用双链回指当日日志，可溯源**。日志本身保留当日的清晰思路。

> 复盘层详细操作见 [[复盘迭代框架]]。

### 4. 架构流程 — 六层数据流

> 与上面三层结构互补：三层架构讲"每个板块是什么"，六层流程讲"数据怎么流"。

```
📥 入口层
   日常事务 ──→ 起念 / 待办事项
   迭代学习 ──→ 待处理笔记 / 起念
   身体数据 ──→ 日复盘
        │
        ↓
📋 捕获层
   待处理笔记（收外部素材·网址·视频）
   起念（收脑内行动想法）
   日复盘（收每日数据）
   待办事项（收明确任务）
        │
        ↓
⚙️ 处理层
   笔记流：待处理 → 常青（#识→#道→#术）/ 系统笔记
   行动流：起念 → 工作/系统迭代/obsidian架构待办 → 日复盘
   行动流·闭环：日复盘改进项（Tasks 📅 明日）→ 次日今日任务 → 勾选完成
   追踪流：日复盘数据 → Tracker 热力图/折线图/汇总
        │
        ↓
🔄 复盘层
   日复盘 → 周复盘 → 月复盘 → 年复盘
        │
   反思分流（所有分流用双链回指当日日志，可溯源）
        │
   ┌────┼────────────────┐
   ↓    ↓                ↓
常青笔记  系统笔记  待处理笔记或起念
        │                │
        └──── 闭环 ──────┘
        输出回流，开启新一轮认知迭代与行动周期
        ↓
🧠 知识层
   常青笔记（#识→#道→#术）· 系统笔记 · 菜谱 · 图书馆
        ↑
        │
🔧 基础设施层（支撑以上所有层）
   模板(10) · Tasks · Tracker · Bases · Templater · CSS
```

## 三、分系统说明

| 分系统 | 目的 |
|--------|------|
| **附件/** | Obsidian 默认附件路径。独立于各模块之外的附件暂存于此（如复制粘贴的图片自动落于此），可归类的附件就近放在对应模块下（见下方附件规则） |
| **框架/** | 总框架定方向，各子框架定具体细节。给自己看，也给 AI 看——快速了解整体布局 |
| **模板/** | 标准化输入格式。常青笔记与系统笔记共用同一模板结构。统一格式、快速录入 |

### 附件存放规则

附件不集中堆放，就近放在对应模块下，便于溯源。

| 附件类型         | 存放位置                                                      |
| ------------ | --------------------------------------------------------- |
| 菜谱图片         | `个人迭代/菜谱/菜谱附件/菜名/`                                        |
| 书籍封面         | `个人迭代/图书馆/书籍附件/`                                          |
| 未归入上述分类的附件   | `附件/`（同时也是 Obsidian 默认附件路径，没有指向粘贴图片自动落于此）                 |

各垂直领域框架应说明自己的附件存放规则。

## 四、维护规则

变更实际文件夹结构、新增/删除模块、调整系统规则后，同步更新本文档，保持总论与实体一致。

### 维护模式

框架默认处于维护模式——不主动改。只有两个解锁条件：

1. **日志把某条原则推成红线**：日复盘/周复盘中反复验证某条原则不可违背，升级为红线后，框架同步修改。
2. **出事故 → 复盘 → 改一处**：实际运转中出了问题，经复盘定位到框架缺陷，只改那处。

认知升级只从实践和复盘来，不从盯框架来。这条规则本身就是解放。

### 三层同步架构

第二大脑的文档体系分为三层，每层和实盘的关系不同：

|         层         | 内容                   | 和实盘的关系                     |   换 AI 工具后    |
| :---------------: | -------------------- | -------------------------- | :-----------: |
|     **L0 实盘**     | 文件/目录/笔记本身           | 唯一事实来源                     |      永远在      |
|    **L1 框架文档**    | `框架/` 下 6 个 .md      | 实盘的说明书——必须对齐，否则任何 AI 都会被误导 | 在 vault 里，跟人走 |
| **L2 Agent的工作日志** | `.workbuddy/memory/` | 过程记录——对齐要求最低               |  换 Agent 就失效  |

**同步优先级**：L1 > L2。L1 不准，则一切操作都建立在对实盘的错误理解上。L2 只记录历史，过时不影响当前操作。
### 新框架建立

新增子框架时，按以下流程操作：

1. **创建文件**：在 `框架/` 下新建 `.md`，按其他框架的格式（导航表 + 四大节）编写
2. **挂载入口**：在 [[#二、系统架构]] 对应层级加 `> 详见 [[新框架]]`，或在 [[#三、分系统说明]] 表格中加链接
3. **更新矩阵**：在 [[#联动修改矩阵]] 加一行，标注该框架需同步的关联文件
4. **通过审查**：对着 [[#框架审查清单]] 逐条自查，完成后在审查结论中记录

删除/合并框架时反向操作：删入口、删矩阵行、更新框架计数。

### 联动修改矩阵

> 以下为框架/模板修改时的同步检查清单。修改任一文件后，须按此清单检查并同步关联文件。

| 修改源 | 需同步的关联文件 |
|--------|---------------|
| **总论框架** | 所有子框架中引用总论锚点的 wiki 链接 |
| **复盘迭代框架** | `模板/日志模板.md`、`模板/周复盘模板.md`、`模板/月复盘模板.md`、`模板/年复盘模板.md`、`.obsidian/snippets/隐藏任务搜索框.css`、`🏠Home.canvas` |
| **笔记系统框架** | `个人迭代/笔记目录/` 下的 .base 文件、`模板/随笔模板.md`、`模板/常青笔记与系统笔记模板.md` |
| **图书馆框架** | `模板/书籍模板.md`、`模板/书摘模板.md` |

| **待办事项框架** | `模板/待办事项模板.md`、`模板/日志模板.md` |
| **任意模板文件** | 所有基于该模板创建的实例 + 引用该模板的框架 |

### 框架审查清单

> 新增/修改框架后，按此清单逐条审查。全部通过即收敛，无需反复检查。
> 审查触发条件：①新框架加入 ②用户主动要求。
> 版本：2026-06-11，以后新增检查项请追加。

#### 维度一：全流程覆盖

| # | 检查项 | 验证方式 |
|:---:|------|------|
| 1.1 | 输入/触发条件是否明确？ | 框架有无说明"什么情况下启动这个流程" |
| 1.2 | 处理步骤是否完整？ | 从触发到结束，每一步有无操作说明 |
| 1.3 | 产出物是否清晰？ | 流程结束产出什么文件、放在哪 |
| 1.4 | 闭环是否成立？ | 产出物能否回流到系统的其他部分（或明确标注"到此为止"） |
| 1.5 | 异常/出错处理是否明确？ | 有异常场景给出处理方式；明确不需要处理则标注免责声明；常见问题有排查指向 |

#### 维度二：链接准确

| # | 检查项 | 验证方式 |
|:---:|------|------|
| 2.1 | wiki 链接指向的文件是否存在？ | 逐一打开验证（`[[框架名#锚点]]` 中"框架名"有对应 .md 文件） |
| 2.2 | 锚点是否匹配目标文件的标题？ | 逐一验证 `#` 后文字与目标文件中的标题完全一致 |
| 2.3 | 路径引用与实盘目录一致？ | 框架中写的 `日志/日复盘/` 等路径在 vault 中真实存在 |
| 2.4 | 模板文件引用是否存在？ | 框架中引用的 `模板/xxx.md` 真实存在 |

#### 维度三：规范清晰

| # | 检查项 | 验证方式 |
|:---:|------|------|
| 3.1 | 文件命名规则是否明确？ | 新人能按规则直接命名文件 |
| 3.2 | 存放位置是否给出具体路径？ | 不是"放在对应目录"而是 `个人迭代/系统笔记/AI使用/` |
| 3.3 | 操作动作是否有对象和步骤？ | "新建笔记 → 填 YAML → 放目录"而非"处理一下" |
| 3.4 | 是否有"与其他框架的关系"对照表？ | 表格列出关联框架和跳转链接 |

#### 维度四：一致性

| # | 检查项 | 验证方式 |
|:---:|------|------|
| 4.1 | 同一概念跨框架表述是否一致？ | 如"待处理笔记"在各框架中叫法相同 |
| 4.2 | 交叉引用是否互为印证？ | A 引用 B 的章节，B 确实有对应内容 |
| 4.3 | 术语是否统一？ | 不会出现"知识笔记"和"知识卡片"混用（除非有意区分） |

#### 维度五：可执行性

| # | 检查项 | 验证方式 |
|:---:|------|------|
| 5.1 | 新人/AI 读一遍能否直接操作？ | 脑中模拟执行，无猜测步骤 |
| 5.2 | 关键操作有无示例？ | 如 YAML 代码块、路径格式、命令示例 |

#### 维度六：审查结论

当前状态标注收敛情况，待审变更记录上次收敛后改了什么（下次只查这些），历史收敛只保留上一次（详细记录，便于追溯）。运作：改框架后在待审变更追加一条 → 触发审查时只查变更框架 → 通过后移入历史收敛（删除旧记录）。
