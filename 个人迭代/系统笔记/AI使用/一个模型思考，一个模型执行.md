# 一个模型思考，一个模型执行

## 核心观点

**把"判断"和"产量"分给不同的模型。** 思考端用满思考强度的高档模型，只做三件事：规划、生成提示词、审查；执行端用任何够用的模型，只做一件事：照提示词生产。执行端**可替换**——今天选 TRAE，明天可以换别的，模式不变。

```
思考端（满思考 GLM-5.3）          执行端（可替换）            交接台
┌──────────────────┐   提示词   ┌──────────────┐
│ 规划：任务怎么拆    │ ───────→ │ TRAE：卡片生成  │ ──→ 产出
│ 生成提示词（小份）  │   桌面     │ Kimi K3：演示  │
│ 审查：过审才入库    │ ←─────── │              │
└──────────────────┘   产出     └──────────────┘
        ↑_________用户搬运（人是管道）_________↓
```

## 为什么这样分

| 痛点 | 解法 |
|------|------|
| 高档模型额度有限（长会话是成本放大器） | 满思考只花在规划/审查这些"错了代价大"的环节，执行不占高档额度 |
| 执行端上下文小、生成慢 | 提示词嚼成小份（一个课时/一个小任务一份），它不用消化大规范 |
| 执行端质量不稳 | 审查是强制关卡：产出回思考端过审（结构/规范/有无编造），过了才入库 |
| 换执行端要重学一遍 | 模式与具体工具解耦——换执行端只换搬运目的地，流程不动 |

## 操作约定

1. **提示词一律放桌面**——用户可见的交接台，不藏深层目录
2. **粒度小份**：一次只喂一个课时或一个小任务的材料＋对应规范切片
3. **审查关卡**：执行端产出先审查（对照规范逐项查），过审才入库/裁图/挂链
4. 执行端跑偏时，回到思考端修提示词再重跑，不手搓执行端的产出

## 场景实例

- **Kimi K3**：交互动画演示（html/css/js，前端最强）——思考端写提示词＋定风格锚点，Kimi 生成，产出验收后入库
- **TRAE**：知识点卡片批量生成（2026-08-26 首用）——TRAE 生成慢、上下文小，正好只当执行端
