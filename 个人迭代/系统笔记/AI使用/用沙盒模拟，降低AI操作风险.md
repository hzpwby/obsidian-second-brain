# 用沙盒模拟，降低AI操作风险

## 核心观点

**测试环境与生产环境分离。** 任何高风险操作——无论是 AI 改文件还是工具大版本升级——都在副本环境中先跑通，确认无误后再作用于正式环境。风险为零，试错无限。

核心模式只有四步：**隔离 → 验证 → 放行/阻断 → 回退**。

---

## 场景一：AI 操作文件

### 问题
AI 操作文件时可能误删、改乱、或者方向跑偏。如果在正式库中操作，出了问题难撤回。

### 方案
建立一个副本 vault（沙盒），AI 在沙盒里自主执行。确认结果没问题后，再手动搬回正式库。

### 具体步骤
1. 复制当前 vault 文件夹到另一个位置（沙盒）
2. AI 在沙盒中执行操作，自由修改
3. 确认结果满意后，问 AI：最终的正确流程是什么
4. 按 AI 给出的流程，在正式库中手动执行一遍
5. 顺手学会这个流程，下次自己也能做

---

## 场景二：Obsidian / 插件大版本升级

### 问题
Obsidian 大版本更新可能导致关键插件（Tasks、Tracker、Templater、Bases）不兼容。插件本身也会自动更新，新版插件可能不兼容旧版 Obsidian。一旦连锁崩溃，日复盘的自动归集、热力图、改进项闭环同时停摆。

仅"回退 Obsidian 版本"不够——插件已经跟着更新了，需要**同时回退插件版本**，很多人会遗漏这一步。

### 多层防御

| 防线 | 操作 | 作用 |
|------|------|------|
| **关自动更新** | Obsidian 设置 → 关闭自动更新；插件也关自动更新 | 防止意外触发，主动权在你手里 |
| **备份 `.obsidian/`** | 把 `.obsidian/` 目录（含所有插件版本）定期打包或纳入 git | 一键回退整个运行环境，不只是 Obsidian 本体 |
| **空 vault 沙箱测试** | 大版本发布后，先用一个空 vault 打开新版 Obsidian，逐一加载核心插件，跑一遍日复盘流程 | 在污染生产环境前发现问题 |
| **降级手册** | 在总论框架中写一段：当 Tasks/Tracker 不可用时，日复盘的最低操作标准是什么 | 即使工具全坏，流程不丢 |

### 空 vault 沙箱测试流程

```
Obsidian 大版本发布
    │
    ▼
① 隔离：用空 vault 或副本 vault 打开新版 Obsidian
    │
    ▼
② 验证：逐一加载 Tasks、Tracker、Templater、Bases
    │  跑一遍日复盘流程，确认查询块、热力图、Templater 变量均正常
    │
    ├── 全部通过 ──→ ③ 放行：升级生产 vault
    │
    └── 任一失败 ──→ ④ 阻断：不升级，等插件适配后重新测试
```

### 为什么不能只靠"回退 Obsidian 版本"

```
Obsidian 大版本更新 → 插件 API 变更
    → 你更新了 Obsidian（不小心自动更新）
    → 插件也自动更新到了匹配新版 API 的版本
    → 你发现 Templater/Tasks/Tracker 坏了
    → 你回退 Obsidian
    → 但插件已经更新了，新版插件不兼容旧版 Obsidian  ← 断在这里
    → 你需要同时回退插件版本
```

这就是为什么**备份 `.obsidian/` 目录**是防线中关键的一环——它包含的不仅是 Obsidian 设置，还有每个插件的具体版本文件。

---

## 两条线的共同模式

| 要素 | 场景一：AI 改文件 | 场景二：工具升级 |
|------|:---:|:---:|
| 隔离层 | 副本 vault | 空 vault |
| 验证内容 | AI 操作结果是否正确 | 插件是否兼容 |
| 放行条件 | 结果满意 + 流程可复现 | 核心功能全部通过 |
| 阻断后动作 | 在沙盒里继续改 | 等插件适配，不强行升级 |
| 回退手段 | 删掉沙盒即可 | 从备份恢复 `.obsidian/` |

---

## 为什么有效
- **零风险**：沙盒崩了不影响正式库
- **可回溯**：AI 跑完之后可以对比沙盒和原库的差异
- **可学习**：不是让 AI 替你干活，是让 AI 先探路，你再跟着走一遍
- **符合盖尔定律**：不追求一次性完美方案，先在沙盒里快速迭代
- **隔绝连锁故障**：工具升级的破坏力被锁在沙盒里，不会传导到生产环境
